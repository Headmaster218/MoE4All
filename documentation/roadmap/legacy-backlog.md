### B1 — `INFR_DN_CHUNK_SCAN` 极性反转

**标签：** CR-N10 · **阻止：** 重大更改扫描

`crates/infr-core/src/config/env.rs`：

```rust
v.dn_chunk_scan = presence_inv(get, "INFR_DN_CHUNK_SCAN");
```

键的拼写是肯定的，但它的存在_禁用_分块扫描 —
只键入名称与其含义相反的文件。它是
R1-frozen（配置活动固定了现有的拼写），因此重命名它是
对于任何已设置的人来说都是重大改变。

**当下一次中断扫描发生时：**重命名为 `INFR_NO_DN_CHUNK_SCAN`，
使其与其他 `INFR_NO_*` 键的 `presence_inv` 语法相匹配
使用。没有别名 - 该项目的环境政策是干净地删除旧拼写
而不是携带它们。

### B4 — 张量并行没有自动覆盖

**标签：** CR-C10 · **被阻止：** CI 硬件

`TensorParallelBackend` 需要 ≥2 个物理 GPU，因此 CI 中没有任何内容可以使用它。
C10 字节计数错误（KV 检查点分配在 `full/W²`，而
副本已移动 `full/W`) 因此未被注意到，并且仅在
不相关的边界防护将其变成了错误。

修复通过对纯部件进行单元测试来实现 - `TpBuffer::len_bytes()`
类型，`shard_bytes`' 可除性保护，以及
`shard_bytes(len_bytes()) == per-rank` 往返 — 但真正的路径仍然是
未运行。

**要做的事：**启用 MTP 的 `--tensor-parallel` 的两 GPU 冒烟运行（即
执行检查点路径的内容）将关闭它。值得手工做一次
即使没有 CI。

### B5 — `infr serve` 没有速率限制

**标签：** CR-S7（部分）· **决定：** 超出此二进制文件的范围

每个请求的挂钟截止日期已到达 (`serve.request_timeout_secs`)，
限制一个请求可以保留 `--parallel` 槽的时间。速率限制 —
限制一个客户端可以发出的请求数量 - 故意没有这样做。

**推理：** 每个将其暴露给网络的运营商都已经有一个反向
代理，这就是连接限制、每 IP 配额和突发控制的地方
属于。在单二进制推理服务器中重新实现它们意味着拥有
已解决的基础设施的更糟糕版本。

**如果出现以下情况，请重新访问：** 有人想要将 `infr serve` 直接暴露给不受信任的人
前面没有代理的流量。这是一个不同的产品决策，而不是一个
缺少功能。

### B6 — 四 token 基准无法可靠分辨低于 10% 的差异

**标签：** 诊断 + 已修复 2026-08-02 · **阻止于：** 无；剩下的是
无人愿意追逐的测量楼层

预填充列的 6.8–34.5% 运行间差异**不是**层
不确定性，这就是该条目最初声称的：`INFR_PROF_OPS=1`
超过六次连续运行产生了相同的字节（操作名称、调度计数）
签名，而吞吐量移动到 1029.5 → 1120.4 t/s，并且没有任何内容供给层
在基准规模上决定实时 VRAM。原因是 `bench_vulkan` 未计时
热身是硬编码的 `(8, 2)` 回合，因此任何其他形状的第一个 TIMED 代表
支付该形状的一次性成本 - 管道变体、首次接触临时池
— 在测量窗口内。通过加热测量的形状来固定。
`pp4@d4096` 峰峰值在四次扫描中分别从 8.4% / 20.2% 上升到 4.3% / 7.9%
方式，最差命名行 (Qwen3.6-35B-A3B UD-IQ3_S) 20.2% → **1.4%**。

**残差，已接受。** Qwen3-0.6B 和 gemma-3-1b 保持 ~8% 峰峰值
`pp4@d4096`。该列乘以 4 个令牌 — 每次代表约 3.7 毫秒墙，其中约 2.8
ms 是设备时间 - 所以大约四分之一是主机端记录/提交/围栏，
剩下的就是它的抖动。选项（如果重要）：为此加注 `-r`
仅
列，报告中位数而不是平均值，或接受四标记
测量结果无法解决低于 10% 的问题。 `infr bench` 打印每次重复的最小-最大
并分布在每一行上，因此这在输出中是可见的，而不是推断出来的。

**超越诊断的方法：** A/B 腿交替至少两次
并报告每次重复，而不是隐藏单个值或平均值
传播。此盒子上的单腿 A/B 错误率为 9% — 该异常值（一个
13 条腿，gemma-3-12b `tg128 @ d8192`，75.9 对 83.0–83.3 簇，
并且这是针对该模型的第一回合运行）是在前缀上测量的
二进制文件并且永远不会重新运行，因此这是该规则的原因，而不是有关的证据
当前树。

### B7 — 深度解码：两种设计被拒绝，一种设计已落地，一种仍处于开放状态

**标签：** 测量于 2026-08-02 · **阻止于：** 无；切片 3a 和 3b 有
已登陆并从此处删除 - 仍然开放的是 (b)，按工作组划分的宽度
计数

llama.cpp 的最大剩余间隙是深度解码，而不是预填充。
Qwen3-30B-A3B Q4_K_M 在 7900 XTX 上对阵 `llama-bench c629da5`、`tg128`
infr/美洲驼: **138.7 / 165.1** @d8192, **106.5 / 140.3** @d16384, **66.9 /
112.1** @d32768 — 深度上下文速度降至基线的 0.60 倍，而 `pp512` 仍与基线一致。（这些数据来自
PRE-slice-3a 基线； `INFR_NO_ATTN_DECODE=1` 复制它们。）
`attn_partial_bda` 是 d32768 处 **59% 的解码 GPU 时间**，并且精确缩放
与 KV 呈线性关系。

**两种设计均被拒绝 - 不要按照书面要求重试。** 均已达到
与参考一致（GQA 位相同，k-tile 为 9.6e-7），因此
他们是正确的，只是速度较慢：

- **GQA 头部分组**，每个（KV 头部，块）一个工作组，覆盖所有
`g = nh/nkv` 查询头：减少 K/V 流量 8 倍（每层令牌 537 → 67 MB）
并测量 **329 µs 与 177 µs — 1.87× SLOWER**。分组序列化8
跨车道减少为之前在 8 个 CU 上运行的一波；重读的
它消除了几乎免费的无限缓存。也不挨饿：
以匹配的并行度重新运行，测得 359 µs，`attn_combine` 继续运行
24.5 → 146 µs，在 8 倍大的 `pacc` 上。每个工作组丢失的密钥也更少
（未分组内核上的块 256：314 µs）。所以无论是流量还是入住率
是控制杆。恢复；树没有改变。
- **LDS 阶段的 K-tile** — 设计 `recorder.rs` 的
`attention_kv_split_impl` 注释名称（“每个线程全点，无跨车道
减少，这就是 llama.cpp 赢得该单元的方式”）。四个配置中最好的一个是
**在 d32768 处慢 2.7 倍**（相对于出厂 184 为 382 µs）。不是一个
实现未命中：ISA 显示 **0 跨通道操作**
`attn_partial_bda` 是 54，所以缩减确实消失了 — LDS 转置
购买它的去除成本比节省的减少更多，因为 K 瓷砖
具有零数据重用（每个字节写入一次，读取一次）并且时间是单调的
LDS 预算中的
（34 KB → 687 µs、17 KB → 494、9 KB → 382）。不连线仍可存活
`tests/attn_ktile_probe.rs` + `shaders/attn_ktile.comp` 因为它是
下一次尝试的测量装置。

**上游基准实际采用了什么**，应直接阅读代码而不是猜测（`ggml-vulkan.cpp`，
`get_fa_tuning_params_scalar`，我们在 RDNA3 上的形状）：`path = FA_SCALAR` — coopmat
**在解码时故意避免**（“标量比 coopmat 更快，当
N==1")，它杀死了该条目曾经提出的矩阵核心/`gqa_ratio` 想法；
`shmem_staging = 0` on AMD，独立证实 k-tile 负面；
`block_rows = 1`、`block_cols = 64`、`workgroup_size = 128`；和
**`d_split = 8`** — 在一个键点上协作的组的宽度，
一项参数在所有实验中均未发生变化。

**`d_split` 扫描**（`shaders/attn_partial_dsplit.comp`，
`tests/attn_dsplit_probe.rs`）产生了两个可分离的发现，并且 `w=32`
控制是它们的区别：

1. **专业化在每个深度都是免费的 6-9%，无需更改算法** —
`w=32` 准确地再现了交付的映射，但击败了它，因为
仅解码副本分配 **96 VGPR 与 120** 且零溢出
方式，因此每个 SIMD 可以容纳更多波。这就是切片 3a/3b 所提供的。
2. **窄宽度仅在工作组并行度较短的情况下获胜**，单调
工作组计数而不是深度：512 wg → 最佳 2.01×，1024 wg → 1.46×，2048
wg → 每个宽度都会丢失。在深度上，内核已经达到约 3.0 TB/s
（Infinity-Cache 速率）并将 Wave 的连续 512 字节 K 读入
`32/w` 段的成本高于较浅的缩减节省。所以 llama.cpp 的
`d_split = 8` 适用于 ITS 配置，但不通用，并且 **
原始 B7 目标 (d32768) 仍然为负**。

**仍然打开 — (b) 按工作组数量划分的宽度。** 从 `nh * n_chunks` 中选择 `w`
针对设备 CU 计数而不是深度。需要塑造探头永远
被覆盖——它只测试了 `nh=32 nkv=4 hd=128`——并且它的每宽度数字是
根据旧参考进行测量，因此比率夸大了剩余的
3a 切片已占用 4-8% 的净空。将其视为中深度杠杆：它
并没有缩小标题差距，其中模型在 d32768 处仍然约为 0.64×。
在再次依靠那个探测器之前，花十分钟在**无法解释的事情上
9.6e-7 在 w=32** 处的漂移 — `attn_decode` 本身是位相同的，并且两者都不是
使每次减少 `subgroupClusteredAdd(., 32u)` 也不常量折叠
`sqrt(float(pc.hd))` 再现它。另请注意 `dsplit_bench` 的“已发货”
参考”腿现在测量为`attn_decode`，因此在下重新运行它
`INFR_NO_ATTN_DECODE=1` 与旧基线进行比较。

**仍然退回到 `attn_partial`** - 每个都需要自己的成员
`attn_decode` 系列：平面 Q8 和主线内联定量 KV（**这就是
gemma 在完整上下文中按 DEFAULT 运行，因此它是最大的剩余覆盖范围
孔**），DiffusionGemma 画布遮罩，`rows > 1`（小 m 规范验证和
预填充），绑定 SSBO（非 BDA）调度，`chunk > 512`（仅在上面可达
`INFR_KV_OVERFLOW` 下的 ~524k 键），除 128/256/512 之外的头部变暗，以及
`window == 0` 层上的 RING 缓存（今天无法访问 — 仅 SWA 层可用）
分配为环 - 并且静态门的行边界拒绝它而不是
假设）。

**运送的内核带有两个陷阱，值得在接触它们之前阅读。**

- hd 256/512 QK 尾循环必须保留 `attn_partial` 的冗余
`if (r < hd4)` 保护并在运行时从推送常量中读取 `hd4`。折叠
对于构建时文字，守卫消失，ACO 将这些术语融合到一个 FMA 中
链，块分数移动 1 ULP — `attn_combine` 的 `exp(m_c - M)`
重量变成 136/2048 不相同的输出。着色器是这么说的；不
“清理干净”。
- `INFR_NO_ATTN_HD=1` 是 **诊断，而不是按位 A/B**。它删除了
用于一般运行时的专用分支 — `hd4` 循环使用不同的归约方式
顺序 — 在 Qwen3.5-9B 上，输出保持连贯且正确，同时
在 396 的生成字节 302 处从已发送的文本中拆分，已发送
和 `INFR_NO_ATTN_DECODE` 字节相等。通过内核名称验证两者
静态和重放门尊重它。成本：d4096 时为 -4.2%，d32768 时为 -11.7%。

**为什么增益是模型形状的：** Qwen3-30B-A3B 为 4–7%，但 gemma 为 ~0.5–1%
并在 Qwen3.5-9B 上进行清洗，因为注意力共享不同（解码 GPU 的 2.9%）
qwen35 上的时间为 d4096，gemma-3-12b 上的时间为 8.7%），不是因为内核更差 —
在 d32768 `attn_decode_hd256` 上优于 `attn_partial_bda` 152.9 vs 167.0 µs
qwen35。 Gemma 的 40 个 SWA 层具有窗口上限（从 d4096 到 18.4 µs 平坦）
d32768)，因此其大部分层不能随深度增长。一个地方的
专业化 LOSES 是高于 d16384 的 gemma — 参见 B15。

### B8 — 完成测量拟合后，部分数值仍依赖估算

**标签：** 重新测量 2026-08-04 · **阻止时间：** 无；下面的每一项都是
有界的工作，目前没有一个导致失败

原始条目声称储备的失控术语是非闪光分数
瓷砖，定价为“最终 ctx 的 2 个实时池”，而真实池“累积”
跨越约 150 多个深层预填充块”。 **两半都错了**，并且
解决它的测量现在是永久机械：
`Backend::activation_peak`（实时 `Activations` 字节的高水位线）和
跑步者的 `activation reserve too low` 警告。每个块的 `execute` 掉落
下一次构建之前的池，并且块的每一层共享一个 `kv_len`，
因此，有一个图块处于活动状态 — 该模型过度保留，在 128 行块中保留了 3.5 倍。

在所报告的 gemma-4-31B UD-Q5_K_XL 外壳上，到底是什么破坏了配合
（以边距 1.0 复制，`bench -p 0 -n 4 -d 19000`，在 4 MiB 上死亡）
分配 **2 MiB** 超过警卫预算）：

| 术语 | 规划师 | 实际 | 德尔塔 |
| --------------- | -------------- | ------------------------------ | ------- |
| 权重 | 21 871 930 488 | 22 353 012 736（217 竞技场大楼） | +481 MB |
| KV | 2 559 590 400 | ~2 504 MB | −56 MB |
| 活化峰 | 911 343 616 | 262 MB | −649 MB |
| 驾驶员侧 | 0 | 加载后 187 MB → PK 时 368 MB | +368 MB |

所以解决方案并不是更好的激活模型：而是停止估计
设备可以询问的事情。 `reclamp_ctx_to_live_room`重新决定
权重上传和KV分配之间的窗口，反对
`Backend::device_alloc_room`。那时仍然可以预测：

- **激活储备**，现在重新拟合到名为 MoE 和的测量峰值
DeltaNet 术语和 1.5x 垫（`ACT_RESERVE_PAD`，按最差拱形确定大小
测量 — Qwen3.5-4B-MTP，1.42x）。
- **`POST_KV_DEVICE_RESERVE`** (256 MiB) — 驱动程序的管道/描述符
在记录第一个转发时构建，在最大的情况下测量为 181 MiB
模型在这里。

**剩下什么，按照重要的顺序。**

1. **每拱激活代数是打地鼠，结构修复是
已知。** `dense_act_reserve_at` 中的每一项都在接口层重新推导了
`runner.rs` 的 `build` 闭包已准确声明 (`g.internal(...)`,
每个 `batch * <width>`)，加上 Vulkan 适配器的 `pooled(...)` 站点
分配。为每个拱门安装它，一下午就发现了三处失误（教育部专家
草稿，qwen35 的 DeltaNet 混合器，qwen35 的双宽度 `qg`/`gate_a` 对） —
每个都被新警告捕获，没有一个被测试捕获。解决方法是对图表进行求和
`Internal` 张量而不是对其进行建模，这需要可构建的图
对于KV缓存存在之前的形状；今天 `build` 是在之后定义的
冷初始化块并关闭 KV 句柄。集中注意力/教育部
术语仍然需要适配器的层谓词（旧选项 1）。
2. **块梯级仍然选择预加载，以对抗轻重量
估计。**购买时重新夹紧可以降低它（`repin_ubatch_lower`）
上下文，但放置的 resident-vs-stream 决策本身没有改变，并且

### B12 — 显式 `--ctx N` 永远不会到达拒绝梯级

**标签：** 于 2026 年 8 月 2 日提出 · **阻止日期：** 什么都没有 - 产品决策是
于 2026-08-12 制作，请参阅本条目末尾的“已决定”

`SeamModel::clamp_default_ctx` 获得拒绝梯级：当 f16 和 q8_0 都不是时
甚至可以提供 `MIN_SESSION_CTX` 令牌，它返回一个命名所请求的 `Err`
上下文，两者都适合，所需的KV字节和权重后的空闲字节，
而不是交还一个不可用的窗口。

它只能看到 MODEL-DEFAULT 上下文。用户提供的 `--ctx N` /
`INFR_CTX=N` 逐字记录 — `vulkan_session_on` 和 `vulkan_slot_ctx`
`SizeSpec::Bytes` 臂都在没有咨询拟合数学的情况下返回它 - 并且失败
稍后在分配时使用通用 VRAM 保护消息。是这样的
其中“拒绝而不是默默降级”最有力量，它就是
一项未涵盖。

默认路径梯级的狭窄也是故意的，不应该
意外加宽：每当受过训练的窗口不适合时就拒绝
打破 24 GiB 卡上的所有普通长上下文模型（Qwen3-30B-A3B 夹
262144 → ~50k 并以 148 t/s 运行； gemma-4-31B 夹紧 262144 → 14 592 并填充
为 30.3 吨/秒）。只有“根本没有可用的上下文”可能会拒绝。

**要做的事：**决定显式超大 `--ctx` 是否应该提前失败
详细消息（路径上的行为更改记录为“从不夹紧
— 用户询问”）或在分配保护方面不断失败。如果提早：检查必须
是可证明的，即单独的精确KV字节+权重> `alloc_room()`，没有
其中有激活储备，因此高估储备永远不会拒绝运行
那会起作用的。

**自 2026-08-04 起，显式路径至少首先是这样说的。**
`reclamp_ctx_to_live_room` 也在其上运行并发出警告，命名执行此操作的窗口
适合设备测量的可用内存，然后再执行所要求的内存
为。上述决定现在只是关于是否将该警告升级为警告
错误 - 它要求的“可证明的检查”正是该路径已经存在的内容
计算。

**2026-08-12（用户）决定。** 不适合 **必须的显式 `--ctx N`
在做任何其他事情之前尝试 q8_0 KV**：_“设置 `--ctx` 时不会
使用 k/v 缓存适合 VRAM，如果愿意的话，将上下文自动量化到 Q8_0
fit."_ 所以显式路径已经走相同的梯子 `clamp_default_ctx`
有 - f16，然后 q8_0，然后拒绝 - 而不是逐字记录并失败
稍后在分配守卫处。量化以服务用户请求的窗口是
优先于夹住窗户；拒绝留在最后一级。

实现：路由 `vulkan_session_on` 和 `vulkan_slot_ctx`
`SizeSpec::Bytes` 通过拟合数学进行臂操作，而不是返回值
逐字记录。上面的两个约束仍然存在——检查必须是**可证明的**
（精确的 KV 字节 + 权重 vs `alloc_room()`，其中没有激活储备），以及
默认路径拒绝梯级不得加宽（只有“根本没有可用的上下文”可能
拒绝，或者每个普通的长上下文模型都会在 24 GiB 卡上崩溃）。

排序注释：这是 `vram-audit-2026-07-12` 中梯子的一级（SWA
→ q8 → 钳制 → 流 → KV-溢出最后），梯级 ORDER 本身就是 B62
请人核实。

### B15 — `attn_decode` 交叉并在 d16384 上方的 gemma 上损失

**标签：** 于 2026 年 8 月 2 日测量 · **阻止于：** 决定 — 门
专业化，或在 gemma 的深层上下文中接受 1.5%

`attn_decode`（B7 切片 3a/3b）与 `attn_partial` 位相同，并且更靠
论文（96 VGPR / 3072 B LDS 对抗 120 / 5120），并且它在每个深度都获胜

**时间去哪儿了。** 在 d32768 处，专用系列的成本为 128 × 335.7 µs +
640 × 18.1 µs = **54.6 ms** 在相同的 768 pass-1 调度中
`attn_partial_bda` 服务时间为 **51.0 ms** — 注意力速度慢 7.1%，这会导致
占设备总数的 +1.4%（229.8 与 226.6 毫秒），并显示为 1.5%
吞吐量损失。 `attn_combine` 未受影响（双腿 9.3 毫秒），因此整个

**全局（非 SWA）层是回归量，参数不需要
建模。** 由于 SWA 内核深度平坦，因此 d8192 → d32768 DELTA
完全属于 128 个全球调度：ON `attn_decode_hd256` 为 79.2
→ 335.7 µs (**+256.5**)，OFF `attn_partial_bda` 的总计为 22.3 → 51.0 ms
（**+224.4 µs** 每个全局调度）。专用内核的扩展性**差 14%
具有深度**。假设两条腿的 SWA 成本相等 (18.4 / 18.4 / 18.5 /
18.1 µs，在 ON 腿上测量）隐含的每次调度全局成本为：

| 深度 | `attn_decode_hd256` | 隐含 `attn_partial_bda` 全局 | 比率 |
| ----- | ------------------- | --------------------------------- | ----- |
| 4096 | 40.1 | ~43 | 1.08× |
| 8192 | 79.2 | ~82 | 1.04× |
| 16384 | 153.4 | ~163 | 1.06× |
| 32768 | 335.7 | ~308 | 0.92× |

**交叉在d16384和d32768之间**，并且端到端tg128一致：1.008×
在 d16384，0.985× 在 d32768。

qwen35，仍在 d32768 上涨。 (c) 追寻占用假设并

### B30 — GGUF 权重 mmap 信任该文件，并且无法强制执行

**标签：** PR#90 · **被阻止：** 没有什么突出的；检测已发货，
阻止一半是故意不尝试

`Gguf::open` 映射模型文件并向其中分发 `&[u8]` 切片以供
测绘的一生。没有什么可以阻止另一个进程写入或截断它
文件：写入会导致内存发生变化，Rust 认为该内存已被冻结，并且截断会变成
常驻页面在下次触摸时进入 `SIGBUS`。该不变量在 `open` 上有说明
并仍然**未执行** — `infr_gguf::watch::WeightWatch` 注意到违规行为，
它并不能阻止它。统计 HELD DESCRIPTOR 而不是路径是
承重选择和 `a_rename_into_place_is_not_a_change` 固定它：
`infr pull` 重命名到位，这会在旧 inode 上留下实时映射
完好无损，因此路径统计会在一个文件替换上大喊狼来了
操作 infr 本身执行。

**已知的检测边界，目前的证据不值得关闭：**

- 相同长度的就地写入（其 mtime 随后被恢复）是不可见的。的
唯一的选择是对每次检查进行千兆字节的哈希处理。
- `serve` 检查每个请求，因此请求中的更改登陆会被
下一个，在该响应已经传输之后。事后检查不会
取消发送。
- `WeightWatch::open` 是 `Gguf::open` 旁边的第二个 `open`，因此重命名
恰好在它们之间着陆，使监视保留在新的 inode 和映射上
旧的 — 一次漏检，从来没有误检，两个系统调用宽。

**考虑并拒绝：将文件复制到匿名映射中。** PR #90
正是这样做的，并且有效，但价格昂贵。在 16 GiB 上测量
Qwen3.6-27B，热页缓存，每次两次：热加载 1.87 秒 → 10.5 秒（5.6x，
重新打开几乎完全关闭的间隙 `model-load-time`)，以及 14 GiB
可逐出页面缓存变成了 20.2 GiB 的匿名 RSS。匿名页面是
仅交换，因此大于 RAM 的模型会从缓慢变为无法运行 — Llama-4
此主机上的 Scout 权重文件为 47.5 GiB，而 RAM 为 60 GiB。恢复于
`5ba6b3f`;保留相同 PR 的张量字节计数溢出检查。

**考虑并拒绝：咨询 `flock`。** `infr` 不能破坏其自身
首先映射 — `pull.rs` 下载到临时目录并重命名，什么也没有
任何地方都会打开一个 blob 进行写入 - 因此锁没有内部写入器发生冲突
与。它并不约束真正重要的作者：
`cp new.gguf live.gguf` 打开目标 `O_TRUNC` 且不加锁，也不
任何编辑器都可以，llama.cpp 也可以。存在可重复使用的机械（`FileLock` 在
`pull.rs`) 如果再次访问此问题，则应将其视为共享 — 独占
将阻止两个 `infr` 进程共享一个模型。 Windows 不是障碍
它第一次出现：`FileLock`已经无条件调用`libc::flock`，所以
`infr-hub` 今天没有在那里构建，CI 仅涵盖 ubuntu-26.04 和
macos-15。

### B-DSV4 — V4 注意力基础操作尚未覆盖的范围（2026-08-10）

**标签：** deepseek · vulkan · 金属 · **被阻止：** 无；范围超出了
操作级专项，明确只“添加基础操作，不在图中发出调用”

这三项新功能中的每一项都位于每个后端的一个内核中
而不是跨越整个注意力/规范/绳索层梯。那是
故意 — 悄悄忽略水槽或标志的层会产生
看似错误的数字，并且还没有调用者来证明扇出的合理性 - 但是
V4 的后续接入也受这些限制。以下每种情况都会明确报错，而不会
无声的后备。

- **Vulkan 上的 `Op::Attention { sinks }`** 仅运行 `attention_kv.comp`
`-DSINKS` 构建：f16 K/V、绑定描述符、静态记录、因果/SWA。
拒绝：Q8_0 或任何其他非 f16 缓存（dequant→f16 prepass 位于下面
路由到接收器内核的早期返回）和 `AttnMask::Canvas`。
`decode_eligible` 对于任何包含接收器操作的图也会返回 false，因此
V4 解码无法复用录制好的计算图。当前没有任何路径能使用 Flash Attention，
非 FA-coopmat、split-K 或 mrows 层，因此汇层运行标量
每个深度一个工作组（行、头）内核 — `attn_partial`
的存在是为了避免。性能通过意味着至少教授 `attn_partial` +
`attn_combine` 水槽（它干净地折叠到联合收割机的最终 `(m, l)` 中，
这是 split-K 部分已经合并的地方）。
- **`Op::Attention { sinks }` on Metal** 仅运行 `ATTN_SINKS_KERNEL` 的两个
实例化（`attention_sinks_f32`、`attention_sinks_f16kv`）。拒绝：a
解耦或量化的 K/V 对、`AttnMask::Canvas` 和解码重放
图缓存。Metal 的支持范围与 Vulkan 相同。
- **Vulkan 上的 `Op::QkNorm { weight: None }`** 是 `rmsnorm.comp` 的 `-DNO_WEIGHT`
仅 f32 版本； f16 `x`（llama4 的后绳 L2 范数形状）错误。 V4的Q
规范读取 f32 `wq_b` 输出，因此还不需要 f16 双胞胎，并且
不构建调度是不构建测试。
- **Vulkan 上的 `Op::Rope { backward: true }`** 仅是静态 f32 NORM
（`rope_back`，`rope_ff_back`）。 NEOX+向后、f16 输出和记录一次
`_dyn` 路径全部错误。 V4 的脱绳在 f32 划痕上是正常的。金属绳是
一个运行时参数化内核，因此它在每条路径上都带有 `backward`
已经。
- **V4 图目前无法录制并重放解码计算图** — 有四类
其操作（`Attention{sinks}`，三个`HyperConnect*`，`Rope{backward}`，
`QkNorm{weight:None}`) 没有 `_dyn` 孪生，所以 `decode_eligible` 是 false 并且
接口层的图缓存准入条件明确排除了 `c.deepseek4`。每个 V4 解码
令牌因此重建+重新编译其图。这是一个真正的每代币主机
成本（胶带要移除的东西）和第一个性能项目
拱门。
- **F16 配重上的 `Op::Linear` 和 `w_off` 在 Vulkan 上仍然被拒绝。** F32
现在骑在一个移动的 `bufferDeviceAddress` 基础上（分组输出
投影的调用者）； F16 在 `matmul_proj` / `linear` / 处需要相同的
`linear_f16_noext`，加上两者的 `w_off % 2 == 0` 义务：
重量为打包 u32 字。今天没有什么能生产出 f16 `w_off`。
- **gemma4 的 V 范数和 llama4 的 L2 范数仍然传递一个向量权重**
`Op::QkNorm`。他们现在可以通过 `None` 并删除每个图的 `head_dim`-float
分配各；这些数字是位相同的（`x * s * 1.0` 是 `x * s`
IEEE，`qknorm_weightless_matches_a_ones_weight` 在
`max_err == 0`）。单独留下，因为它是对 `crates/infr-llama/src` 的编辑，
不属于操作级专项的范围。
- **Metal 从未被执行过。** 没有可用的 Apple 硬件；三个
新内核（`qknorm_nw_f32`、`rope_f32` 的 `backward` 臂以及两个
`ATTN_SINKS_KERNEL` 实例化）类型检查通过
`cargo check -p infr-metal --all-targets --target x86_64-apple-darwin`，和
MSL 在运行时在设备上编译，因此 macOS CI 作业是他们的第一个真正的作业
编译并第一次执行。三个 `#[ignore]`d 测试
（`qknorm_weightless_parity`、`rope_backward_parity`、`attention_sinks_parity`）
将会报告它。

### B-DSV4-HC — Sinkhorn 超连接操作尚未覆盖的范围（2026-08-10）

**标签：** deepseek · vulkan · 金属 · **被阻止：** 无；范围超出了
操作级专项，明确只“添加操作，不在图中发出调用”

`Op::HyperConnectMix` / `HyperConnectPre` / `HyperConnectPost` 已实施
并在 CPU 和 Vulkan 上通过一致性测试（在 Metal 上进行类型检查）。尚待完成的工作：

- **加宽的流如何进行种子化是一种假设，而不是转录。**
ratio-0 发出复制所有 `hc_mult` 流中的令牌嵌入
（每个流 `Op::CopyStrided`，在序言中）。 `documentation/architecture/models/deepseek-family.md` 都没有 §
第 4 阶段也不是这个文件记录了 `deepseek4.cpp` 在那里实际做了什么——
读取专项覆盖了压缩缓存、注意力块和 HC 运算，
不是流初始化。复制就是超连接
表述要求以及什么使头部的崩溃成为统一的分区
位于深度 0，但尚未根据源进行检查。 **阅读
`deepseek4.cpp` 的 `build_arch_graph` 序言并在信任之前确认它
真实的 V4 检查点的输出。** 错误的种子会产生合理的 logits。
- **压平的 `hc*n_embd` 行上的失重 RMSNorm 变为
Ones-Vector 方式**，而不是 `Op::RmsNorm { weight: Option<_> }` 方式：一
每个 V4 会话都会上传 `hc_mult*n_embd` 范围的 1.0 向量，与
三个一向量 gemma4 / Dual-MoE / llama4 已上传。延伸
`Op::RmsNorm` `Op::QkNorm` 的扩展方式将放弃该分配
所有四个调用者，并且是更整洁的最终状态；它超出了这里的范围，因为
这是对每个后端的更改。
- **根本没有考虑性能。** 每个内核都是朴素的形状：
`hyper_mix` 每个令牌运行一个线程，并在私有中使用 `hc × hc` 矩阵
数组（动态索引到私有数组是经典的临时内存
spill) 和 `hyper_pre` / `hyper_post` 是每个输出元素的一个线程
串行 `hc` 项循环且无向量化。在 `hc = 4` 混合操作是
`rows × 24` 工作浮动，所以这不太重要； `hyper_post` 写入
`rows × hc × n_embd` 是第一个测量的。这里什么都没有
测量。
- **`hc_mult` 由主机签入限制为 `HYPER_CONNECT_MAX_MULT` (8)**
每个后端。提高它意味着在 `hyper_mix.comp` 中提高 `HC_MAX` 并且
`elementwise_norms.metal` 一起 — 该常量被复制为三个
地方（Rust、GLSL、MSL）之间没有编译时链接，只有主机
拒绝将玉米粒保持在范围内。
- **`Op::HyperConnectMix` 写入三个输出。** Vulkan 的 `dispatch` 处理
尾随 `n_out` 绑定作为写入，而 Metal 采用显式写入掩码，因此
危险跟踪是正确的——但这是代码库中的第一个操作
超过两个 `dst`，并且没有为其寻找融合/调度通道。
- **Metal 从未被执行过。** 没有可用的 Apple 硬件；四个
新内核（`hyper_mix_f32`、`hyper_mix_gates_f32`、`hyper_pre_f32`、
`hyper_post_f32`) 类型检查通过
`cargo check -p infr-metal --all-targets --target x86_64-apple-darwin`，和
MSL 是在运行时在设备上编译的，因此 macOS CI 作业是他们的第一个真正的作业
编译并第一次执行。三个 `#[ignore]`d 测试
`crates/infr-metal/tests/parity.rs` (`hyper_connect_mix_parity`,
`hyper_connect_pre_parity`、`hyper_connect_post_parity`）将报告什么
它。
- **`n_iter` 不会在 40 以上执行，而 `eps` 仅在 1e-6 / 1e-2 时执行。**
真实的 V4 值来自 `{arch}.hyper_connection.sinkhorn_iterations` 和
`.epsilon`，两者都没有从真正的 GGUF 中读取（参见§“打开
问题“`documentation/architecture/models/deepseek-family.md` 中的 1 — 没有转储 V4 文件）。
- **这四个 eps 站点并非全部固定在生产 eps 上。** 在 `eps = 1e-6`
过度 dst 站点将答案移动了 ~3e-7，低于 1e-5 容差
后端比较运行于；仅合成 `eps = 1e-2` 外壳可将其固定
f32 内核。与非对称迭代 COUNT 相同（~1e-11 at 1e-6）。两者都
由 `hyper_connect_details_are_load_bearing` 以精确算术固定。如果
一个真正的 V4 GGUF 结果使用了一个小 eps，一个丢弃了
over-dst eps 将通过这里的所有测试。

### B-DSV4-HASH — 哈希路由 MoE 与 SwiGLU 限幅尚未覆盖的范围（2026-08-13）

**标签：** deepseek · vulkan · 金属 · **被阻止：** 无

哈希路由现在在 CPU + Vulkan 上发出并生成：`Op::GatherI32`
（`gather_i32.comp` 和 CPU 解释器臂）读取令牌的行
`blk.N.ffn_gate_tid2eid` 进入 `[batch, n_expert_used]` 选择
`Op::MoeFfn::expert_ids` 消耗，并且 `generate_dense_backend` 不再
拒绝哈希路由层。参见 `documentation/architecture/models/deepseek-family.md` 第 4 阶段的“阶段 A2”。尚待
剩下
：

- **`Op::GatherI32` 在金属上被拒绝**，按名称，在 `run_op` 中。实施它
单独将故障转移到一个操作之后，而不会使任何工作起作用：
Metal DEVICE `Op::MoeFfn` 路径置位 `MoeGating::Softmax` 并且 V4 的门控是
强制 `SqrtSoftplus`，因此 V4 MoE 层无法以任何方式运行（
该条目自 2026 年 8 月 10 日以来已记录相同的拦截器）。谁举起
sqrt-softplus断言也拥有收集——它是一个小的MSL内核，或者是一个
`Op::MoeFfn` 现有主机后备旁边的主机臂，已经
实现 `expert_ids`。
- **该 gather 没有 `_dyn` 版本，也未纳入图重放支持。**
它属于 `decode_eligible` 的 `_ => {}`，即它被视为
重放安全（它是：位置无关，并且其 `ids` 输入是相同的缓冲区
`Op::EmbedGather` 在链式解码下读取）。没有什么可以锻炼，
因为 V4 还因另外四项限制而完全无法使用图缓存（§
B-DSV4）。待 V4 支持图缓存后再重新检查。
- **收集每步每个哈希层运行一次，未融合且未测量。** 所有
`hash_layer_count` 层在同一 `n_used` 处收集相同令牌的 ID
宽度，因此整个选择可以是对堆叠表的一次调度（或
跨层缓存）而不是每个层进行一次调度。在`hash_layer_count = 3`
已发送的文件，该文件是 6 个线程的 3 次调度 — 预计是噪音
在教育部本身旁边，但没有任何轮廓。
- **该表被读取为一个绑定存储缓冲区**，而不是通过
驻地-BDA竞技场。精细于 `n_expert_used * n_vocab` 双字（3.1 MB
发布的文件，8 MB，256k 词汇和 `n_used = 8`)，以及 `Recorder::vkb`
根据设备的实际 `maxStorageBufferRange` 断言范围 - 但是
触发该断言的未来表将需要一个 `-DSTREAMED` 双胞胎，其中
不存在。
- **重新考虑主机收集替代方案并再次拒绝。** 令牌
ids 现在在每个 V4 路径上都是主机已知的（V4 既不记录一次
图缓存也不支持链式解码，因此每一步仍会经过逐 token 循环
主机刚刚喂饱了 `cur[pos]`），所以主机聚集会起作用
没有新内核。拒绝，因为它需要一个额外的图形输入和一个
每个哈希层额外的每步上传，每个表的主机反量化，以及
因为当 V4 获得 GPU 驻留解码时，它必须被撤消 —
其中采样的 id 永远不会到达主机。设备采集成本一小
着色器并重用已存在的 ids 输入。
- **仅执行了 `batch == 1`。** `Op::GatherI32` 被写入任何
`rows`，且操作级一致性测试使用 `rows = 2`，但完整模型
路径是每个令牌：V4 被排除在批量预填充之外（§ B-DSV4-WIRING），并且
`build` 断言如果没有 ids 输入，则无法构建哈希路由范围，
分块预填充无处可绑定。重新启用批量 V4 预填充
意味着给 `PfChunk` 一个与其嵌入的主机分开的 ids 缓冲区
行。

- **`Op::io` 仍然省略 `exp_probs_b`。** 预先存在的（列出了 `x`，
`router_x`、`router`、三个银行和`down_scale`)； `expert_ids` 是
补充说，`exp_probs_b` 故意留下来，因为超出了范围。重要的只是
用于多设备管道执行器，它推断每个操作的设备并剪切
来自 `Op::io` 的张量 — 管道边界上的 `exp_probs_b` 不会
标记为已读。没有附带的管道配置可以跨a路由deepseek2/3 MoE
切，所以这从未被解雇过。

Metal 上真正的 V4 MoE 层将在该断言处中止，即使使用收集
在手。无论如何，散列路由和钳位都是在那里实现的（`moe_topk`
`hash` 标志、`gatedact_f32` 的 `do_clamp`/`limit`) 和
`moe_ffn_hash_routing_parity` 覆盖了 softmax 形状； sqrt-softplus

- **Metal 从未被执行过。** 没有可用的 Apple 硬件。的
更改了内核（`moe_topk`、`gatedact_f32`、`gatedactfused_f32`）类型检查

MSL 在设备上编译，因此 macOS CI 作业是他们的第一个真正的编译和
第一次执行。 `gatedact_swiglu_clamp_parity` 和

**在 GLSL 中重复**（`attn_live.comp` 在 GPU 上重新计算它），所以

dp4a 但**从不** MFMA（仅限 CDNA/MI 系列）并且从不 RDNA4 的 WMMA 一代
(RX 9000)。

具体来说，这意味着无论多少，以下内容都在此保持未经验证
工作已完成：`infr` 的 `coopmat_bf16` 和 `coopmat_f8` 层，其字段文档
已经说过，它们在所有 RDNA4 之前的硬件上都是 `None`，并且其调度是
选择加入，特别是因为“此开发框没有”（在 `adapter.rs` 中读取）
`bf16cm_ok` 评论）。任何声称这些等级正确的说法目前都是
仅编译时声明。

没有别的——相同的调度形状，相同的绑定，相同的推送常量：

- **一次通过，而不是两次。** 标量构建在关键范围内行走两次（一次用于
行最大值，一次取幂），计算每个 `sq · K[j]` 点两次。这
层带有运行最大值和运行分母，并通过以下方式重新缩放 `sv`
`exp(m_old − m_new)` 提高最大值的键 — 相同的在线 softmax
`attn_flash_partial.comp` 已使用。

是一个 128 通道共享内存树，每次传递每个密钥花费 9 `barrier()`，18
每个键总共
。该层对每个屏障的密钥进行评分 `MLA_SG_KB`（
`subgroupAdd` 每个，然后一个乒乓跨子组修复），所以它支付一
每 8 个键的屏障 — 以及寄存器中批次的 V 贡献总和，
将 `sv` 的 8 次读取-修改-写入变为 1 次。

`MLA_SG_KB` = 8 是通过扫掠选取的，其他所有内容均保持不变（每个重复 3 次）：

层调度，比之前的 5.6 毫秒和 97.3% 下降。在预填充 (`-p 2048`) 时，它是
**86.8%**，每次调度 2.08 秒或 2.40 秒，38.5 毫秒，从 50.1 毫秒到 89.4%。所以
内核仍然是框架，没有被触及的形状是
第一个命名的原始条目：**每（行、头）一个工作组**，即
`n_head` = 解码时 96-CU 部件上有 16 个工作组，约 83% 的设备空闲。
`Op::Attention` 的 split-K 分解 (`attn_partial` + `attn_combine`, chunk

`split_pm`/`split_pl`/`split_pacc`）是可参考的实现；`Op::Mla` 目前没有对应分支
它。注意预填充不能是一个占用故事——那里有 16384 个工作组——所以
split-K 臂仅购买解码行。

**测量但未发货：将获取的 K 跨过障碍物。** V 是
同一K行的前导`kv_lora_rank`列，因此V累加重新读取
列出已获取的分数循环。将它们保存在寄存器中
(`kk[MLA_SG_KB][MLA_SG_VSLOTS]`) 已实施并在 `MLA_SG_KB` = 8 上进行测试：
pp512 857.2、pp2048 955.3、tg64 130.9、tg64 @ 2048 13.8 — 即 **+12% pp2048 和
与发货形式相比 +17% tg64@2048，但 −18% pp512**，相对于发货形式的回归
它在短提示行上替换的内核。出货回归的形式
什么也没记录，并在这里记录了交易，而不是捍卫 12% 的预填充损失。

其机制尚不清楚，并且明显的假设被排除：
`RADV_DEBUG=shaderstats` 报告 **两种形式的 96 VGPR 和 0 划痕**（
mla build 是转储中最大的计算着色器 — 代码大小 18548 与
14692 重读），因此每个 SIMD 的占用率和寄存器压力相同
不能作为解释。修剪可证明已死亡的第五个保留插槽已移动
pp512 by 3 t/s (857.2 vs 854)，这也表明寄存器不是杠杆。
谁拿起这个：两种形式仅在 V 循环上有所不同，因此选择
在 `rows`/`kv_len` 上（`flash_min_rows` 和 `rows >= 64` 门的方式已经
`Op::Attention` 的工作）会双赢——但首先要找到机制。

**没有尝试过，下一个廉价的想法：** `kread` 每列发出一个双字负载
并扔掉一半 — f16 缓存将每个相邻的列打包在一起
`uint`。为每条车道提供一对相邻的列，而不是步长 128
single 会将加载指令数彻底减半。 `key_len` 已经
需要为偶数（`kread` 将行寻址为 u32 对），因此形状
允许。

- **`Op::Mla` 和 `Op::LightningIndexer` 各自取消图表的资格
记录一次解码重放 — 并且几乎不需要花费任何成本。**
`adapter.rs` 中的解码资格循环返回 false，对于所述
原因：MLA使用非标准内核，索引器烘焙其因果关系
在记录时间从 `pos` 推送常量绑定，没有参数驱动的 `_dyn`
双，因此重放的计算图会使用录制时绑定的键
在。因此，每个 DeepSeek 解码令牌都会重建并重新记录其图形 - 但是
`INFR_PROF_STAGES` 价格重建为 **0.039 ms/tok 或 8.9 ms/tok**
解码步骤，0.44%，均来自同一运行。单独的 `INFR_PROF_OPS` 运行
将 GPU 设置为 8.2 ms/tok，这推断（跨运行，因此探查器自己的
开销就在其中）记录+提交是唯一的另外 ~0.7 毫秒和重放
图缓存带来的整体收益上限不到 10%。应先从内核层着手；
这不是 DeepSeek 解码问题。

**第三个成本是通过测量发现的，并且已修复**（`session_stable` 的
`moe_batched_ok` in `seam/runner.rs`): 专家库 dtype 扫描运行了 EVERY
层，因此DeepSeek的领先密集块（`Config::is_moe_layer` false，无
`ffn_*_exps` 要查找的张量）读取 `None`，扫描失败，并设置
`batched_prefill_ok` 对于每个 DeepSeek 模型都是 false — 整个提示是
每次提交预填充一个令牌。前后交替测量：V2-Lite
第512页39.1→975.5（25×），第2048页12.3→673.4（54×）； `deepseek` V1
（`mradermacher/deepseek-moe-16b-chat-GGUF` Q4_K_M，相同的密引线形状，无
MLA) pp512 229.0 → 4185.0，与 llama.cpp Vulkan 的 4320.07 ± 相同
该型号为 358.49。解码不受其影响（tg64 111.0 → 111.2）。 V1
一致性对照很有参考价值：批量 MoE 路径本身没有问题，因此 V2-Lite 的
剩余预填充间隙也是`mla.comp`。

**内核自身一致性测试的覆盖缺口，在接入时就已发现
层。** `recorder::tests::mla_matches_cpu_reference` 是 DeepSeek-SIZED
调度 (`kv_lora_rank` 512, 16 个头) 并且它是饱和的：它的合成 q 和
K 使两个参与键的分数相差约 1e7，因此 softmax 是一个硬
argmax，无论分数如何，输出都是获胜者的 V。乘法
内核中每增加 1.01 分，其 `max_err` 就恰好为 0 —
测试根本看不到分数路径缺陷，只能看到 V/吸收/布局缺陷。 （它
已经带有一条评论，出于不同的原因担心这种形状。）
`mla_ring_and_mask_matches_cpu_reference` 确实捕获了它（相同的扰动
将其带到 `max_err` 1.97e-4 对抗 1e-4 层），因此该对被覆盖 —
但是大形状测试并不是其尺寸所暗示的防护。修复将是缩放
其综合输入使分数彼此相差几个单位。

**校准，因此这不会被解读为比它更落后：** llama.cpp's
**Vulkan** 后端同样没有融合索引器（参见 B-DSHW-FUSED-REF）。`infr` 与 llama.cpp 的
CUDA 后端存在差距，与其 Vulkan 后端相比则没有这一差距。

### B-DSV2-ACTIVATION-PRECISION — int8 激活并非 DeepSeek 缺陷；`cfg.deepseek2` 的 f16 实现方案已否决（2026-08-11，2026-08-12 关闭）

**标签：** deepseek · 参考 · **阻止：** 无；这是一个决定
记录和排除列表，不是缺陷

该条目曾经是 B-DSV2-DEGENERATE —“DeepSeek-V2-Lite 输出衰减为
Vulkan 上的重复”。 **该症状已修复**，但其原因尚未修复
激活精度：`MixerW::Mla`中的`seam/runner.rs`推送了自己的
`Op::Add{a: hidden, b: sub, dst: hidden}` 并进入共享
后混合器残差添加，因此注意力输出进入残差流
在两个后端的每个 DeepSeek2 层上两次。 2026-08-12 删除；的
命名此条目的一代现在读取
Vulkan 上的

```
The sky appears blue because of a phenomenon called Rayleigh scattering. When
sunlight enters the Earth's atmosphere, it collides with molecules and small
particles in the air. …
```

（`--temp 0 --max-new 60`、`Why is the sky blue?`），CPU 运行
有一个词不同（“现象”的“过程”）——一场接近平局的翻转，而不是
退化。 `gpu_seam_matches_cpu_deepseek2` 测量整个词汇
CPU/Vulkan 余弦在 55 个令牌的天空段落上 **0.99861**，与
0.9385 在修复之前以 56 个代币记录，并且该提示 + 0.99 下限
现在是测试的内容。

值得保留的是途中被排除的一切，每一个
测量，加一判定。

#### 激活精度引线已失效 — 不要重新打开它

Vulkan `Op::Linear` int8 激活预传递的读数 (`quant_q8`,
每 32 块对称）是基于第 0 层隔离的错误，显示
int8 路线相对于 f64 参考结果的 L2 误差为 6.423e-3，其中
f32 激活 GEMV 为 9.081e-8。关于 MATMUL 的隔离是正确的，并且
结论是错误的。两次独立的测量杀死了它，都采取了
当双倍残差仍在树中时：

**1。取消 int8 的每个激活并没有修复输出，并且几乎没有移动
协议。** Whole-vocab CPU-vs-Vulkan 在 llama.cpp 自己的 56 上对余弦
天空散射段落的 token id，每行一个模型加载：

| 激活途径 | cos(cpu, vk) | 第512页 | tg64 |
| -------------------------------------------------------------------- | -----------: | --------- | ----- |
| int8 `quant_q8` + dp4a mmq（默认发货） | 0.9385 | 977.6 吨/秒 | 111.5 |
| f16（`INFR_NO_MMQ=1` → coopmat GEMM，f16 A 分期） | 0.9503 | 968.0 吨/秒 | 111.6 |
| f32 (`INFR_NO_COOPMAT=1 INFR_NO_MMQ_FALLBACK=1 INFR_MOE_SMALL_M=64`) | 0.9625 | 708.6 吨/秒 | 111.2 |

所有三个仍然首尾退化。性能一栏是诚实的价格
每个：f16 成本 **1.0% pp512**，f32 成本 **27.5%** — 后者复制
测量到的恢复的`exact_linear_acts`标志的-28%，这是
证实这一行确实是全 f32 激活路线。

覆盖范围是经过检查而不是假设的。 `mmq` off 删除唯一的 int8
密集线性臂 Q4_K 预填充可以装在这个盒子上（`nc_mmq` 需要
`!f16_coopmat()`，这在 RADV 上是错误的）； `moe_small_m = 64` 全程路线
56 行 MoE 到 `linear_native_id_multi` 的本机块 f32 GEMV，而不是
`quant_q8_gather` + `matmul_mmq_experts`; m=1 解码 GEMV 已经
AMD 上的 `linear_native`（`mmv_mw_choice` 返回 `None`，`mmv_decode` 默认值
off），这就是 tg64 在所有三行上都是平坦的原因。 `gemm_warp` 关闭在顶部
f16 行更改了输出位一致（cos 0.951823 两次），即没有
扭曲瓦片形状一开始就发挥了作用。

**2。 llama.cpp 的 Vulkan 后端在此处使用相同的 int8 激活预通道。**
在引脚 030ebb5 处读取。 ZZZ保持0ZZZ
(`ggml/src/ggml-vulkan/ggml-vulkan.cpp:9172`) 将 `quantize_y` 设置为
`device->integer_dot_product && src1 is contiguous f32 && (ne11*ne10)%4==0` 和
然后首先尝试 mmq 管道，没有性能启发式 - 它仅被降级
如果该数据类型不存在 q8_1 管道，而 Q4_K 有一个。 ZZZ保持0ZZZ
是每 32 块对称 `d = amax/127` 量化器，而 `mul_mmq_funcs.glsl` 的
Q4_K 臂是 `dotPacked4x8EXT` 整数点。大门是
`VK_KHR_shader_integer_dot_product` +
`integerDotProduct4x8BitPackedSignedAccelerated`，默认打开（终止开关：
`GGML_VK_DISABLE_INTEGER_DOT_PRODUCT`)，RADV 满足。解码是一样的
在每个供应商 `k` 阈值后面预通过（`ggml_vk_should_use_mmvq`：AMD 使用
int8 一次 `k >= 2048`)。一种永远不会在以下位置获得 int8 激活的架构
预填充是 coopmat2 (NVIDIA `VK_NV_cooperative_matrix2`)，它强制转换
src1 到 f16 at `ggml-vulkan.cpp:9163` 并且根本不构建 q8_1 管道。

所以 **infr 的 int8-activation 默认值与上游没有分歧**：
相干参考实现以完全相同的方式减少激活
正是这个硬件。

#### 已通过测量排除的方向，无需重新尝试

- **`mla.comp` 不是缺陷。** 两次独立检查。 (1) DeepSeek 大小
扫描（`n_head` 16、`kv_lora_rank` 512、`qk_nope_dim` 128、`qk_rope_dim` 64、
`v_head_dim` 128) 超过 `kv_len` 2…2048，带或不带 `-DFREQ_FACTORS`
构建，针对 f64 参考：最大相对误差 6e-7…4e-6。 (2) 真实的
第 0 层 `Op::Mla` 输入（`q`、f16 KV 行、`wk_b`、`wv_b`、
`freq_factors`、`rows`=59、`kv_len`=59）从CPU后端自己捕获
CPU 分支并通过 `Recorder::mla` 重放：每行余弦相似度均为 1.00000000
CPU的输出，最大绝对误差1.8e-7。
- **不是 YaRN 主干尺度，不是绳索类型，不是 freq_factors 斜坡** —
在固定修订版中从 llama.cpp 中读出的每个常量并与
infr 发送的内容：`kq_scale` 0.11472137 均在两者上，
`llama_model_rope_type(LLM_ARCH_DEEPSEEK2)` 是 `LLAMA_ROPE_TYPE_NORM`
(`neox: false`)，并且 infr 的 `yarn_ff` 除数再现 `rope_yarn_ramp`
恰好 (p=0 → 1.0, p=11 → 1.081081, p≥23 → 40.0)。
- **不是着色器内 Q4_K WEIGHT dequant。** `native_decode.glsl` 的 `dqblk` 是
从设备中读出真实的每个元素
`blk.0.attn_kv_a_mqa.weight` (Q4_K, 2048→576) 通过调度
`native_gemv.comp` 具有一次性激活：1179648 个元素，**0 不是
与 `infr_gguf::dequant::dequant_block` 位相同**。
- **不是 `Op::EmbedGather` 对 `token_embd` 的反量化** (Q4_K, 2048×102400): 64
行分布在 GPU 上收集的词汇表中，131072 个元素，**0
不相同**。
- **不是 `attn_norm` 上的 `Op::RmsNorm`**：真实重量、真实嵌入行、eps
文件中的
，针对 f64 参考 — 最大相对误差 2.365e-7
（256 线程预填充构建）/1.191e-7（`-DWIDE` 解码构建）。

所有三个 dequant/norm 结果均由
`crates/infr-vulkan/tests/weight_dequant_parity.rs`，每个断言都是
在被信任之前显示为红色。

#### 考虑并拒绝

**登陆`cfg.deepseek2`的f16激活路线** 几乎免费
（上面测量的 pp512 的 1.0%，vs f32 的 27.5%）及其 matmul 确实更多
比int8准确。拒绝：它没有修复报告的错误（残留
做到了），它的 CPU 协议增益在提示长度上甚至不是单调的（更糟糕
比 int8 在 len 16 和 32 处更好，在 56 处更好），上游在这个精确位置上发布 int8
路径。如果后面的切片想要对其进行 A/B，则该控制杆已以 `INFR_NO_MMQ` 形式存在
再次
——不需要建造任何东西。

#### 覆盖范围差距，明确说明

- `weight_dequant_parity` 仅覆盖 Q4_K。所有其他格式的 `dqblk` 臂都在
`native_decode.glsl` 仍仅与另一个 Vulkan 版本进行比较
(`weight_addr_parity`)，从不与宿主对抗。
