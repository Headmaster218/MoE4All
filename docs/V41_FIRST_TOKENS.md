## Round 29：140.7 ms 合理吗？不合理，慢了 15–40 倍

### 先取真实维度（不再用估计值）

从 GGUF 元数据直接读：

```
deepseek41.embedding_length        = 5120
deepseek41.expert_feed_forward_length = 2304
```

（此前用 4096/7168 估的，都不对。）

### 每次调用的计算量

一次 `native_idm_iq1m_paged` 处理 `physical_slots = rows × 7 = 1792` 个槽，
每槽是一次 `[1 × 5120] × [5120 × 2304]`：

```
总 MAC = 256 × 7 × 2304 × 5120 = 21.14 G MACs
```

### 带宽核算：不是瓶颈

```
单专家 gate 权重 = 2304 × 5120 × 1.5625bit / 8 = 2.20 MiB
最坏情况全部 1792 槽各读一份 = 3.85 GiB
140.7 ms 内完成 => 27 GB/s
```

**显卡带宽上限约 450 GB/s。即使最坏情况，带宽也远没用满。**

### 算力核算：这才是问题

| 假定的 int8 峰值 | 21.14 GMAC 应需 |
|---|---|
| 10 TOPS | 4.2 ms |
| 20 TOPS | 2.1 ms |
| 30 TOPS | 1.4 ms |

**实测 140.7 ms ⇒ 等效算力只有 0.30 TFLOPS。**

**慢了 15–40 倍。**

### 结论

`native_idm_iq1m_paged` 的 140.7 ms **既不是带宽造成的，也不是总计算量造成的**。

最可能的解释：**1792 个独立的 `1 行 × 5120 × 2304` 乘加**。
每个槽只有 1 行，算术强度极低——`1 × n_embd × nff` 的乘加喂不满 SIMD，
和 Round 9 在 CPU 侧遇到的「m=1 时网格解码成为瓶颈」是同一类问题。

### 注意边界

- **已确定**：140.7 ms 远超带宽和算力所能解释的范围（15–40 倍）
- **未验证**：int8 峰值取 10/20/30 TOPS 是保守估计，B70 的真实峰值未实测；
  若真实峰值只有 1 TOPS，结论会不同。**这是本轮最薄弱的假设。**
- **未验证**：kernel 内部是否真的按 1792 个独立 GEMV 执行，需要读 kernel 或做 A/B

### 下一步

在动内核之前，先确认一件事：**把 rows 减半，这个 kernel 的时间是否也减半？**
- 若线性 → 确实是按槽数计的固定成本，问题在每槽效率
- 若不到一半 → 有固定开销，可先摊薄

这比直接改 shader 便宜得多。
