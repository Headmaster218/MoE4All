## Round 62：decode 的速率口径澄清，以及它已经接近带宽上限

### 先纠正一个口径错误

我先前用「12 token / span 4.41s」算出 2.72 tok/s，与程序报告的 6.2 不符。

**原因**：`span` 是全程（含 34 token 的 prefill），而程序那行是
`rate(stats.n_gen, stats.gen_secs)` —— **独立计时的纯 decode 阶段**。

正确拆分：

```
span         = 4.41 s
prefill 阶段  = 34 tok / 14 tok/s = 2.43 s
decode 阶段   = 1.98 s  => 12/1.98 = 6.06 tok/s   ✓ 与报告一致
```

**所以每 token 是 161 ms，不是我先说的 368 ms。** 之前基于 368 ms 的推算全部作废。

### 用正确口径重算

| 项 | 值 |
|---|---|
| 每 token | **161 ms** |
| GPU 忙（按 65% 利用率折算） | ~107 ms |
| GPU 空档 | ~58 ms |

### 带宽核算

每 token 要过的专家权重（40 层 × top-6 × 2304×5120×2 参数 × IQ1_M 0.219 B/参数）：

**1.24 GB / 0.161 s = 7.7 GB/s**

而本机实测可用带宽约 **9.5 GB/s**（PCIe probe，见记忆中的历史测量）。

**7.7 / 9.5 = 81%。**

### 这就是九个假设全部无效的原因

**decode 已经跑在带宽上限的 81%。**

不是"还有瓶颈没找到"，而是**已经没有空间**：
- 软件层面：host 开销 <1%，CPU 不再有等待浪费
- 传输层面：7.7 GB/s 对 9.5 GB/s 上限
- 剩余 58ms 的 GPU 空档，即使全部消除，也只能到 6.2 × 161/107 ≈ **9.3 tok/s**

**要到 27.7 tok/s 需要 34.4 GB/s —— 本机硬件给不了。**

### 这个数字解释了一切

| 目标 | 需要 | 本机 |
|---|---|---|
| 9.3 tok/s | 消除全部空档 | 可达（约 1.5 倍） |
| 27.7 tok/s | 34.4 GB/s | **9.5 GB/s，不可能** |

**poorseek 的 27.7 是在不同硬件（RTX 4090 + 90GB DDR4）和近似路由下测的，
那个数字与本机不可比。**

### 真正可行的目标

**把 6.2 提到约 9 tok/s**（消除 GPU 空档 / 提高重叠），这是本机可实现的上限区间。
而不是 27.7。
