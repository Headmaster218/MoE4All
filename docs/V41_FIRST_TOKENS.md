## Round 157：最小输入（5 个 token）上就分叉 —— 排除长序列累积类原因

### 最干净的对照：`Hi`

prompt 编码成只有 5 个 token：

```
[0, 128803, 23166, 128804, 128821]     (BOS, User, Hi, Assistant, think)
```

| 配置 | top5 | 熵 |
|---|---|---|
| 参考 `strata-dsv41` | **304:63.6%, 295:19.0%, 4888:7.3%** | **~1.9** |
| moe4all（engram on） | 2619:6.3%, 201:4.7%, 1492:3.2%, 139:2.9%, 666:2.6% | 6.340 |
| moe4all（`ENGRAM_ZERO=1`） | 16:20.8%, 201:4.3%, 28:3.4%, 342:3.3%, 14:3.1% | 5.077 |

参考引擎自己生成的序列是 `2581, 1309, 3287, 304`，最后一行 logits 又强烈预测"再来一个 304"。

**两边零交集，而且置信度差一个量级：参考 63.6%，moe4all 6.3%。**

### 这组数据的价值：排除了一整类原因

输入只有 5 个 token。在这个长度上：

- **压缩注意力**：ratio-2 层要到第 2 个 token 才写第一行压缩缓存，ratio-4 层要 4 个，
  源层/复用层的状态推进最多走 1–2 步 —— 不足以解释这么大的偏差
- **engram 前驱窗口**：ngram 最远 4，前驱几乎为空
- **位置编码累积 / RoPE 长程畸变**：位置只有 0–4
- **KV cache 回绕 / 分页**：远未触及

**全部排除。** 分歧发生在**最基本的一次前向**里。

### 同时排除的假设

- **`Dsv4CacheWrite { rows: 1 }` 在压缩路径中的同类问题**：在 5 token 上压缩缓存最多写 2 行，
  即便写法有误也不足以造成这种量级的分歧（该处仍值得后续清理，但不是本 bug 的原因）
- **"压缩状态随长度累积变坏"**：用 2 / 31 / 121 字符三档 prompt 测，熵保持 6.34/6.41/6.46，
  没有随长度单调恶化的迹象

### 现在的结论

**问题出在单次前向的基础计算里，且表现为"信息丢失"而不是"数值放大"** ——
参考引擎在同样输入上给出 63.6% 的强信号，moe4all 只有 6.3% 的平坦分布。

下一步应当在这 5 个 token 的输入上做逐层观测：把每层残差流的范数打出来，
找第一处与"输入信息应当如何被放大"不符的地方。5 个 token 的序列足够短，
使这个观测在计算上可行且不引入缓存类干扰。
