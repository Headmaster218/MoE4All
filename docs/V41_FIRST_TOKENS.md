## Round 183：严格对齐输入上的第一个 A/B —— engram 在污染残差流

### 输入（逐 token 验证相同）

```
[0,128799,3476,477,260,11502,22896,16,128803,3085,344,270,6102,294,8760,33,9361,295,834,2004,16,128804]
```

### 结果

| 配置 | top-5 | 熵 |
|---|---|---|
| **基线** | `201:8.49%, 344:4.04%, 304:3.47%, 16:3.04%, 734:2.67%` | 6.405 |
| **INFR_ENGRAM_ZERO=1** | `51119:28.17%, **16:28.06%**, 201:4.44%, 671:3.43%, 344:3.11%` | — |
| 参考 `strata-dsv41` | 生成 `271, 5, 223, 19, 16, 10793` | — |

### 解读

**关闭 engram 后置信度从 8.49% 涨到 28.17%（3.3 倍），且 `16` 升到第 2 名
—— `16` 正是参考引擎生成序列里也出现的那个 token。**

**⇒ engram 参与计算，但把残差流推向错误的方向。**

**但 `51119` 不是正确答案** —— engram 是 V4.1 的正确架构组件，关掉它只是去掉污染源，
不是修复。真正的缺陷是 **engram 的计算结果本身错了**。

### 与前几轮的关系

- Round 170 修的是 engram 的**缓冲越界**（写 60 KiB 到界外）→ 置信度 6.31%→17.18%
- 本轮测的是 engram 的**计算结果**（假设把输出置零）→ 置信度 8.49%→28.17%

**两件事叠加说明：engram 这条路径错得很深，不止一处问题。**

修完越界后 engram 不再破坏内存，但它的**语义输出仍然不对**。

### 下一步

需要判断 engram 输出的**量级**是否合理（相对残差流）。若 engram 注入远大于残差流本身，
就是缩放 bug；若量级合理而方向错，则是 gather/投影逻辑错。

**这个判断需要读 engram 的中间值 —— 而逐层观测工具三轮尝试均失败
（`Internal` 张量不可绑定，Vulkan 后端只把 `Output` 张量绑定到可下载缓冲）。**

**在拿到这个数值之前，对 engram 的任何进一步修改都是猜测。**
