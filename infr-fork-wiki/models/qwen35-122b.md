# Qwen3.5-122B-A10B APEX-I Quality

[首页](../README.md) / [模型](README.md) / Qwen3.5-122B

## 目标

在 RX 7900 XTX 24 GiB、约 20 GiB 可控 VRAM 预算、45～51 GiB RAM 预算下运行一个
122B/A10B MoE。该模型的 routed-expert payload 为 72.36 GB，超过可用 RAM；因此它是
三级缓存、按尺寸多池、shared fusion、ordered trace 和 Host DMA 的综合验收模型。

## 几何结构

2K cold trace 使用的缓存几何：

| 项目 | 值 |
|---|---:|
| Routed-expert payload | 72.36 GB |
| Expert layers | 48 |
| 每层 routed experts | 8 |
| 每 expert roles | Gate + Up + Down |
| GPU pool | 15.53 GB，7910 usable slots |
| Bounded inclusive RAM | 54.76 GB（配置 51 GiB） |
| Pool 0 | 1.7 MB block，4613 GPU / 16272 RAM slots |
| Pool 1 | 2.2 MB block，1647 GPU / 5811 RAM slots |
| Pool 2 | 2.6 MB block，1646 GPU / 5811 RAM slots |

三个 pool 对应 GGUF 中三类实际 matrix block size。slot 容量按模型 metadata 和真实 byte
size 计算，不再硬编码 35B 的 Q5/Q6 几何。

## 冷启动到 2K 的真实 trace

条件：20 GiB VRAM budget、51 GiB bounded RAM、Q8 KV、context 4096，从无 `infr.exe`
进程开始，70 prompt tokens + 2048 Decode。

| 指标 | 结果 |
|---|---:|
| Request wall | 193.139 s |
| Server Decode | 11.2 tok/s |
| 最后 5 秒窗口 | 多数 11.7～12.5 tok/s |
| Ordered accesses | 2,441,088 / 98,448 pager calls |
| Decode-only GPU hit | 69.573% |
| Request RAM conditional hit | 96.596% |
| Request SSD reads | 24,993 blocks |
| Request SSD traffic | 约 50.227 GB |
| SSD reads / generated token | 约 12.20 blocks（含一次 request prefill route） |

这条 trace 解释了为什么最初观测只有 12～13 tok/s：不是“预热多跑几千 token 就一定会
到 30”，GPU hit 在后半程仍约 67～70%，路由工作集持续变化；SSD miss 虽只占总 access
约 1%，单次成本却高得多。

## 正确性问题：连续输出 `!`

长运行曾出现输出退化。根因不是统一 VRAM slot 搞乱，而是 Qwen hybrid recurrent state
在 empty cache/reset 后没有与 KV 生命周期一起重置。`1accc8c` 补充 state reset，随后 2K
trace 输出正常 prose，访问序列无不连续或 backward call id。

这个修复说明：混合 Attention/DeltaNet 模型的“上下文状态”不只有 KV；recurrent state
必须与 session cache reset 具备同一生命周期语义。

## Shared expert 融合

原逻辑让 shared expert 走独立计算和累加步骤。它与 routed expert 的数学结构相同，仅
权重 dtype/物理来源可能不同，因此新增 mixed-dtype descriptor 后可在同一 batched UGD
计算中处理 shared + resident routed experts。

ABBA tg256：

| 版本 | A | B | 均值 |
|---|---:|---:|---:|
| Fusion off | 17.0 | 17.3 | 17.15 tok/s |
| Fusion on | 19.2 | 19.2 | 19.20 tok/s |

提升约 11.5%～12.9%。收益来自少一次独立 dispatch/同步/accumulate，并扩大 resident batch；
不是 Q8 被转换成 Q5/Q6 后再算，kernel 仍按各自量化格式原位解码。

## Resident-first UGD 调度

当前通用策略：

1. shared + 已 resident routed experts 作为完整 UGD batch 先算；
2. CPU 同时批量晋升所有 miss 的完整 UGD；
3. 晋升结束后，miss experts 作为第二个完整 UGD batch 计算并累加。

为什么没有实现“RAM miss 先 UG、计算 UG 时搬 D，SSD miss 则全等”：微基准显示 122B
完整 9-expert UGD 仅 69～120 µs，而 1-expert RAM UGD 已 353～523 µs，SSD 是
1.689～2.753 ms。UG 本身更短，再加第二次 submit/CPU hand-off 后通常倒亏
0.1～0.75 ms（RAM）或 0.6～3.1 ms（SSD）。见
[调度微基准](../reference/moe-schedule-microbench.md)。

## Host DMA 路径

### 问题

旧 bounded RAM cache 通过 CPU 把 host bytes 复制到 mapped ReBAR。生产微基准约
14.3～14.7 GiB/s；纯 Vulkan copy 对足够大 payload 可到 23～25 GiB/s。

### 改造

- RAM cache 本身按 Vulkan external-host alignment 分配；
- 用 `VK_EXT_external_memory_host` 将原 buffer 原位 import；
- `vkCmdCopyBuffer` 从 imported host buffer 搬到统一 GPU expert arena；
- 未 import 的后缀继续使用并行 CPU→ReBAR；
- import failure 是性能 fallback，不是加载失败。

Windows 驱动的总 import ceiling 约 29 GiB。最初 first-come 让第一个大 pool 吃掉额度，
后续 pool 几乎全走 fallback；`497460a` 改为选择“当前 import 覆盖比例最低”的 pool。

| 指标 | First-come | Proportional |
|---|---:|---:|
| tg256 | 22.4 tok/s | **23.2 tok/s** |
| Import total | 约 29/45 GiB | 28.99/45 GiB |
| 三池覆盖 | 极不均匀 | 62.6% / 67.7% / 64.9% |

按比例分配较 first-come 再提升 3.6%；相对 shared fusion 后 19.2 tok/s，最终 23.2 是约
20.8% 的进一步提升。

## 还剩什么瓶颈

- imported prefix 使用 DMA，RAM cache 后缀仍走 CPU push；
- copy 与 compute 当前主要使用同一 Vulkan 主队列，没有成熟的独立异步 transfer pipeline；
- cold/长对话仍会遇到 SSD miss，tg256 不能替代 2K trace；
- IQ4_XS block 较小，但现有 Decode kernel 比 Q5_K/Q6_K 慢：9-expert UGD 约 120 µs，
  Q5_K/Q6_K 分别约 69/88 µs；
- GPU hit 只有约 70% 时，RAM→VRAM 仍是最大单项之一。

## 结论

122B 的 23.2 tok/s 不是“122B 已完全摆脱 storage”，而是证明同一 20 GiB 级 VRAM 预算
下，正确的 shared fusion、全局 pool、bounded RAM/SSD 和 Host DMA 能把短基准推进到实用
区间。真实长运行仍应同时报告 cold trace/SSD demand。
